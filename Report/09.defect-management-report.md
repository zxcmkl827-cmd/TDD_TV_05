## 3. 결함 분류 체계 정리

### 3.1 Severity 정의

| Severity | 정의 | 릴리스 영향 |
|---|---|---|
| Critical | 크래시, 미정의 동작, 핵심 모듈 빌드 불가, 데이터 손상 | 릴리스 차단 |
| Major | 핵심 기능 불능, 전체 CI/CTest 실패, 회귀 테스트 다수 실패 | 조건부 차단 |
| Minor | 경계·예외 정책 미구현, 잠재 결함, 단일 테스트 미작성 | 비차단 |
| Info | 문서·명명·스타일 개선, 관측 정보 | 영향 없음 |

### 3.2 Severity 매트릭스

|  | 높음: 크래시·UB·빌드 불가 | 중간: 기능 오동작·테스트 실패 | 낮음: 엣지·정책 미정 |
|---|---|---|---|
| 프로덕션 코드 | Critical | Major | Minor |
| 테스트/빌드 인프라 | Major | Major / Minor | Info |
| 문서·요구사항 | Major | Minor | Info |

### 3.3 상태 전이

```text
New -> Open -> In Progress -> Fixed -> Verified -> Closed
                    \-> Won't Fix / Deferred
```

각 상태의 의미는 다음과 같습니다.

| 상태 | 의미 |
|---|---|
| Open | 결함 확인, 수정 또는 Red 테스트 대기 |
| Fixed | 코드·빌드 수정 완료, 검증 전 |
| Verified | 회귀 테스트·커버리지 게이트 통과 |
| Closed | 원장 반영 및 이슈 종료 |

## 4. 결함 보고서 템플릿

신규 결함은 `docs/defect_list.md`에 등록하고, 상세 내용은 아래 항목을 기준으로 작성하도록 정의했습니다.

| 필드 | 설명 |
|---|---|
| ID | `DEF-TV-###`, `DEF-BLD-###` 형식 |
| Severity | Critical / Major / Minor / Info |
| ItemType | Runtime / UB, Build Defect, Test Infrastructure, Spec Gap 등 |
| Status | Open / Fixed / Verified / Closed |
| Steps | 재현 조건, 입력, 실행 명령 |
| Expected | 요구사항·테스트 계획 기반 기대 동작 |
| Actual | 실제 실패 결과, 로그, 실패 테스트명 |
| Root Cause | 원인 파일·메서드·분기 |
| Fix Summary | 수정 요약, 커밋 해시 |
| Verification | `ctest`, Mock, coverage 결과 |

템플릿은 `docs/defect_report.md` §2.2에 Markdown 복사용 블록으로 포함했습니다.

## 5. 품질 메트릭 수집 계획

### 5.1 핵심 메트릭

| 메트릭 | 정의 | 목표 |
|---|---|---|
| 테스트 통과율 | `Passed / (Passed + Failed + Not Run)` | 100% |
| Line Coverage | `TVController.cpp` 실행 라인 비율 | 90% 이상 |
| Branch Coverage | 분기 커버리지 | 85% 이상 |
| 함수 커버리지 | 대상 함수 실행 여부 | 100% |
| 단계별 결함 발견율 | 단계별 신규 Open 결함 수 / 실행·검토 건수 | 추세 관리 |
| Critical 잔존 | Open Critical 결함 수 | 0 |

### 5.2 테스트 통과율 수집

로컬 최소 게이트:

```powershell
cmake --build build
ctest --test-dir build -R "ControllerTest|TVControllerMockTest|TunerTest" --output-on-failure
```

전체 스위트:

```powershell
ctest --test-dir build --output-on-failure
```

`Not Run`은 통과율 분모에 포함하며, `all_tests_NOT_BUILT` 같은 항목은 빌드/테스트 인프라 결함으로 추적합니다.

### 5.3 단계별 결함 발견율

| 단계 | 활동 | 발견 유형 |
|---|---|---|
| Unit | `TVControllerTest`, `TunerTest` | 로직, 경계값, UB |
| Integration | Controller + Fake/Mock `Tuner` | 협력 계약, 문자열 정책 |
| System | Golden Master, Approval Test | 복합 시나리오 회귀 |
| Static/Build | 컴파일, CMake, 경고 | 빌드 결함 |
| Requirement Review | 요구사항 분석 대조 | Spec Gap |

계산식:

```text
발견율(단계 X) = 단계 X에서 최초 등록된 결함 수 / 단계 X에서 실행·검토한 테스트 케이스 수
```

### 5.4 C++ 커버리지: gcov/lcov

gcov/lcov 기반 수집 절차를 문서화했습니다. MSVC 네이티브 환경은 gcov가 없으므로 WSL, MSYS2, Linux CI 환경 사용을 권장합니다.

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build
ctest --test-dir build -R "ControllerTest|TVControllerMockTest" --output-on-failure

lcov --capture --directory build --output-file build/coverage.info
lcov --remove build/coverage.info \
  '*/test/*' '*/googletest/*' '*/gmock/*' '*/ApprovalTests/*' \
  --output-file build/coverage.filtered.info

genhtml build/coverage.filtered.info --output-directory build/coverage_html
lcov --summary build/coverage.filtered.info
```

현 CMake 기준으로는 `TVControllerTest`에만 `--coverage`가 적용되어 있으므로, 향후 `TVController` 라이브러리 타깃에도 커버리지 플래그를 부여하는 개선을 권장합니다.

## 6. GitHub Issues 연동 방안

GitHub Issues 사용 시 `defect_list.md`의 DEF-ID와 Issue를 1:1로 연결하도록 정의했습니다.

| 결함 원장 | GitHub Issues |
|---|---|
| `DEF-TV-001` | `[DEF-TV-001] PressNextFavorite wrap UB` |
| Severity | `severity:critical` 등 label |
| ItemType | `type:defect`, `type:build` |
| 모듈 | `module:tvcontroller`, `module:ci` |
| Status | Project 상태 또는 `status:*` label |

권장 흐름:

```text
Red 테스트 / ctest Fail
-> defect_list.md Open 등록
-> GitHub Issue 생성
-> PR에서 Fix + 테스트 추가
-> ctest + lcov 검증
-> defect_list.md Verified
-> Issue Close
```

PR 체크리스트와 `gh issue create` 예시는 `docs/defect_report.md` §4에 포함했습니다.
