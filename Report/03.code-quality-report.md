## 2. 분석 요약

`TVController`는 리모컨 숫자 입력 버퍼링, 채널 적용, 선호 채널 CRUD·순환을 **단일 클래스**에서 처리합니다.

**잘 된 점**

- `Tuner&` 추상화 의존(**DIP**) — Mock/Fake 주입으로 테스트 가능
- 메서드 길이 대체로 5~15줄 — 현 시점 **Long Method 없음**

**개선 필요**

- **SRP:** 숫자 FSM, 채널 검증/적용, 선호 채널 저장·탐색이 한 클래스에 혼재
- **OCP:** `remoteKey` 미사용, README 확장 시 메서드·분기 증가 예상
- **매직 넘버·센티널:** `-1`, `0`, `99`, `10` 및 `stoi`/`sort` 중복
- **치명 이슈:** `PressNumber()` 내 컴파일 오류 문자 `햣`, `PressNextFavorite()`의 `end()` 역참조(UB)

> **매직 넘버 참고:** 질의에 언급된 `50`, `11`, `6`은 `TVController` 본문에 없습니다. `50`은 `test/TunerTest.cpp` Mock 반환값, `6`·`12` 등은 테스트 시나리오 채널 번호입니다. 본 클래스 리터럴은 **`-1`, `0`, `99`, `10`** 입니다.

## 4. SOLID 분석

### 4.1 SRP (단일 책임 원칙) 위반

| 책임 | 현재 위치 | 변경 이유 |
|------|-----------|-----------|
| 숫자 입력 상태 머신 | `PressNumber`, `PressConfirm`, `PressOthers` | 입력 규칙·자릿수 정책 변경 |
| 채널 유효성·튜너 적용 | `ApplyChannel`, `IsValidChannel` | 유효 범위·`Tuner` API 변경 |
| 선호 채널 영속 | `FavoriteChannels`, `PressFavorite`, `AddFavoriteChannel` | CRUD·정렬 정책 변경 |
| 선호 채널 네비게이션 | `PressNextFavorite` | 순환·wrap 규칙 변경 |

한 클래스에 **최소 4가지 변경 이유**가 있어, 선호 채널만 수정해도 숫자 입력 코드에 손대야 할 위험이 있습니다.

### 4.2 OCP (개방-폐쇄 원칙) 위반

- 공개 API가 `PressNumber`, `PressConfirm`, `PressFavorite` 등 **고정 메서드 집합**
- `remoteKey` enum은 `include/remoteKey.h`에 있으나 루트 `TVController`는 **미사용** (레거시 경계, 구조 변경 금지)
- `Report/02` 기준 미구현: 채널 검색, 업/다운 → 신규 동작마다 클래스 수정 필요

**권장:** `void OnKey(remoteKey k)` + `unordered_map<remoteKey, Handler>` 테이블로 확장 시 기존 핸들러는 닫고 행만 추가.

### 4.3 잘 지켜진 원칙

| 원칙 | 근거 |
|------|------|
| **DIP** | `Tuner&`에만 의존, `DevTuner`/`MockTunerForController` 주입 |
| **LSP** | `Tuner` 계약 내 구현체 교체 (단위·Mock 테스트로 확인) |

## 5. Code Smell 분석

### 5.1 Long Method

현재 **해당 없음** (대부분 5~15줄). README 확장(3자리·검색 FSM) 시 `PressNumber` 비대화 **잠재 위험**.

### 5.2 Duplicated Code

```cpp
// PressConfirm / PressNumber(2nd digit) — 버퍼 확정 패턴
int SelectedChannel = ChannelBuffer;  // 또는 ChannelBuffer * 10 + ch
ChannelBuffer = -1;
ApplyChannel(SelectedChannel);

// PressFavorite / AddFavoriteChannel
FavoriteChannels.push_back(...);
std::sort(FavoriteChannels.begin(), FavoriteChannels.end());
```

### 5.3 조건문 복잡도

| 메서드 | 복잡도 | 비고 |
|--------|--------|------|
| `PressNumber` | 낮음 | `ChannelBuffer == -1` 1단계 분기 |
| `PressFavorite` | 중간 | 토글 + erase-remove |
| `PressNextFavorite` | **높음(버그)** | 잘못된 `end()` 분기 |

| 값 | 위치 | 의미 | 상수화 권장명 |
|----|------|------|---------------|

## 7. C++17 개선 방향

### 7.1 단기 (동작 동일·가독성)

```cpp
enum class DigitBufferState { Empty, OneDigitPending };
std::optional<int> bufferedDigit_;  // -1 센티널 제거

namespace tv {
  constexpr int kMinChannel = 0;
  constexpr int kMaxChannel = 99;
  constexpr int kDecimalBase = 10;
}
```

### 7.2 중기 (OCP·확장)

**테이블 기반 디스패치**

```cpp
using KeyHandler = std::function<void(TVController&)>;
const std::unordered_map<remoteKey, KeyHandler> handlers = { /* ... */ };
```

**`std::variant` FSM** (검색·다중 상태)

```cpp
using ControllerState = std::variant<
    struct Idle {},
    struct DigitBuffered { int first; },
    struct ScanResultPending { std::vector<int> hits; }
>;
```

### 7.3 전략 패턴 (책임 분리, 선택적)

| 전략 | 역할 |
|------|------|
| `IChannelApplicator` | 유효성 + `tuner.setCH` |
| `IFavoriteStore` | sorted unique insert/remove/next |
| `IDigitInputPolicy` | 1/2/3자리·선행 0 |

`TVController`는 Facade로 축소. **현 규모에서는 전면 전략 패턴은 과설계**일 수 있으나, `Report/02` 미구현 범위를 고려하면 **FavoriteStore + 키 테이블**이 비용 대비 효과적입니다.

### 7.4 기타 C++17

- `[[nodiscard]]` on `GetFavoriteChannels()`
- `Tuner`가 `std::string` 고정이므로 `string_view`는 레거시 경계 밖에서 검토; 우선 `GetCurrentChannelInt()` 래퍼

## 11. 결론

`TVController`는 **DIP 기반 테스트 가능 구조**를 갖추었으나, **SRP·OCP** 측면에서 책임·확장성 개선이 필요합니다. 즉시 수정 대상은 **컴파일 오류 문자**와 **`PressNextFavorite()` UB**이며, 이후 **선호 채널 로직 분리·매직 넘버 상수화**를 거쳐 `Report/02`의 미구현 기능(검색·업/다운)을 **테이블 디스패치·variant FSM**으로 확장하는 것이 권장됩니다.

**핵심 결론**

1. **선행 수정** — 빌드 결함·순환 UB는 `Report/02` 기능 확장 및 TDD 전에 반드시 처리  
2. **SRP** — `FavoriteChannelStore`·`ChannelInputBuffer` 분리로 변경 범위 축소  
3. **OCP** — `remoteKey` handler 맵 + 필요 시 `std::variant` 상태  
4. **상수화** — `-1`/`0`/`99`/`10`을 named constant 또는 `optional`로 치환  
5. **추적성** — `docs/code_quality_report.md`와 본 보고서를 `Report/01`·`02`와 함께 리팩토링·테스트 작업의 기준 문서로 사용  

향후 구현·리팩토링 시 **우선순위 1 → 2 → 3** 순으로 진행하고, 각 단계마다 기존 테스트 스위트를 Green으로 유지하는 것을 권장합니다.
