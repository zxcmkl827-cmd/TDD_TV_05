## 2. 프로젝트 배경

### 2.1 시스템 구성

셋탑박스 TV Controller는 리모컨 입력을 해석해 채널을 변경하고, 외부 `Tuner` 모듈에 실제 채널 설정을 위임합니다.

```text
리모컨 입력
    └── TVController (도메인 로직)
            └── Tuner 인터페이스 (외부 제공)
                    ├── DevTuner (Fake, 테스트용)
                    └── MockTuner (Google Mock)
```

### 2.2 Tuner 인터페이스 계약

`Tuner`는 문자열 기반 API를 사용합니다.

| 메서드 | 역할 |
|---|---|
| `seekCH()` | 현재 채널에서 증가 방향으로 시청 가능 채널 검색 후 변경, 검색된 채널 문자열 반환 |
| `setCH(const std::string& ch)` | 지정 채널로 현재 채널 변경 |
| `getCurrentCH()` | 현재 채널 값 문자열 반환 |

Controller는 채널을 `int`로 계산한 뒤 `Tuner` 호출 직전에 `std::string`으로 변환합니다. 이 경계가 문자열 관련 결함의 주요 발생 지점입니다.

### 2.3 채널 유효 범위

일반 채널은 **0 ~ 99** (총 100개)입니다. 범위 밖 값은 `std::invalid_argument` 등으로 거부해야 합니다.

## 3. 기능 요구사항 요약

### 3.1 숫자 버튼 채널 변경

| 시나리오 | 입력 | 기대 결과 |
|---|---|---|
| 한 자리 + 확인 | `1`, 확인 | 채널 1 |
| 두 자리 자동 확정 | `1`, `2` | 채널 12 (확인 없이 즉시 변경) |
| 네 자리 연속 | `1`, `2`, `3`, `4` | 12 → 34 순서로 변경 |
| 세 자리 (홀수) | `4`, `5`, `6` | 45 변경 후 `6` 대기 |
| 세 자리 + 확인 | `4`, `5`, `6`, 확인 | 45 변경 후 6번 |
| 세 자리 + 기타 버튼 | `4`, `5`, `6`, 기타 | `6` 무효화 |
| 선행 0 | `0`, `7` | 채널 7 (`"7"`, `"07"` 아님) |

**구현 핵심:** `ChannelBuffer`로 한 자리 대기 상태를 관리하고, 두 번째 숫자 입력 시 `first * 10 + second`로 즉시 확정합니다.

### 3.2 선호 채널

| 동작 | 조건 | 기대 결과 |
|---|---|---|
| 선호채널추가 | 현재 채널이 선호 목록에 없음 | 추가 |
| 선호채널추가 | 현재 채널이 이미 선호 목록에 있음 | 삭제 (토글) |
| 다음선호채널 | 현재보다 큰 선호 채널 중 최소값 | 해당 채널로 이동 |
| 다음선호채널 | 더 큰 값 없음 | 가장 작은 선호 채널로 순환 (예: 56 → 1) |

**구현 핵심:** `std::upper_bound`로 다음 선호 채널 탐색. 목록은 정렬·중복 제거 상태 유지.

### 3.3 채널 검색

채널검색 버튼 입력 시 `Tuner::seekCH()`를 반복 호출해 시청 가능 채널 목록을 저장합니다.

**QA 관점 주의:** 무한 루프 방지(최대 100회 또는 시작점 복귀), 중복 채널 제거, 빈 결과 처리가 필요합니다.

### 3.4 채널 업/다운

| 조건 | 업 동작 | 다운 동작 |
|---|---|---|
| 검색 결과 없음 | `current + 1`, 99→0 순환 | `current - 1`, 0→99 순환 |
| 검색 결과 `{4, 6, 14}` | 현재 6 → 14 | 현재 6 → 4 |
| 검색 결과 있음, 현재 목록 밖 (15) | 4로 순환 | 14로 순환 |

**구현 핵심:** 검색 결과 유무에 따라 일반 채널 순환과 저장 목록 기반 이동을 분기합니다.

## 4. 문자열 변경 시 주의사항

`Tuner` API가 `std::string`을 사용하므로 Controller 구현·테스트 시 다음을 반드시 고려해야 합니다.

| 항목 | 위험 | 권장 |
|---|---|---|
| `std::to_string(int)` | 선행 0 제거 (`0`,`7` → `"7"`) | 정수로 관리, `setCH()` 직전에만 변환 |
| `std::stoi(string)` | 빈 문자열·비숫자·범위 초과 시 예외 | 파싱 경계에서 예외 정책 명시 |
| `to_string(remoteKey)` | `std::to_string`과 이름 혼동 | `std::to_string(ch)` 네임스페이스 명시 |
| Mock 기대값 | `setCH("7")` ≠ `setCH("07")` | 숫자 의미와 문자열 직렬화 정책 일치 |
| 예외 메시지 | 구현마다 상이 | GTest에서는 타입·상태 위주 검증 |

## 5. 예외 및 경계값 조건

### 5.1 채널 범위

| 조건 | 기대 동작 |
|---|---|
| `0`, `99` | 유효, 설정 가능 |
| `-1` 이하, `100` 이상 | 유효하지 않음, `std::invalid_argument` 또는 `setCH()` 미호출 |

### 5.2 입력 버퍼

| 조건 | 기대 동작 |
|---|---|
| 버퍼 없음 + 확인 | 채널 변경 없음 |
| 버퍼 있음 + 숫자 외 버튼 | 대기 숫자 무효화 |
| 숫자 API에 `0~9` 밖 값 | 예외 또는 무시 정책 정의 필요 |

### 5.3 선호 채널·검색

| 조건 | 기대 동작 |
|---|---|
| 선호 목록 비어 있음 | 다음 선호 채널 no-op |
| 검색 결과 비어 있음 | 업/다운은 일반 채널 기준 |
| `getCurrentCH()` 비정상 반환 | `stoi` 예외 — Controller 정책 별도 정의 |

## 8. 테스트 전략 권고

### 8.1 Test Double 선택

| 목적 | 사용 | 예 |
|---|---|---|
| 최종 채널·선호 목록 상태 | Fake (`DevTuner`) | `EXPECT_EQ("12", getCurrentCH())` |

1. 시나리오 1~3: Tuner 경계값 (이미 상당 부분 존재, 보강)

3. 시나리오 15~17: 다음 선호 채널 순환 (버그 수정 포함)
4. 시나리오 18~19: 채널 검색 (신규 API + Fake)
5. 시나리오 20~27: 업/다운 (검색 결과 유무 분기)
6. 시나리오 28~30: Mock no-op·예외 정책

## 10. 결론

`README.md`의 TV Controller 요구사항을 C++17·Google Test 관점으로 재정리하여, 구현 계약·문자열 경계·예외 조건·30개 테스트 시나리오를 문서화했습니다.

**핵심 결론:**

1. **문자열 경계** — `int` ↔ `std::string` 변환은 `Tuner` 호출 직전/직후에만 수행하고, Mock 기대값은 `"7"` vs `"07"` 구분을 명확히 해야 합니다.
2. **기능 갭** — 채널 검색·업/다운 및 연속 숫자 입력 시나리오는 요구사항에는 있으나 테스트·구현이 부족합니다.
3. **테스트 로드맵** — `docs/requirements_analysis.md`의 30개 시나리오를 TDD Red 단계부터 순차 반영하는 것이 QA 관점에서 권장됩니다.
4. **선행 수정** — `TVController.cpp` 컴파일 오류 가능 문자 및 `PressNextFavorite()` 순환 로직은 기능 확장 전에 수정·테스트로 보호해야 합니다.

향후 구현·리팩토링은 본 보고서와 `docs/requirements_analysis.md`의 시나리오 번호를 기준으로 진행하면, README 요구사항과 테스트 커버리지의 추적 가능성을 확보할 수 있습니다.
